# How Limitwick works

## Refresh and notifications


The panel shows the time remaining first, then the local reset time: only the time for a reset today, the weekday within the next six days, and the date otherwise (with the year only when it differs). If a reset time has passed, wait for a successful refresh to confirm the next one. Limitwick refreshes after waking and normally every three minutes; repeated failures lengthen the delay to at most 24 minutes. Refresh in the context menu remains available between requests.

Settings can enable separate low-quota and confirmed-reset notifications. Both are off by default. The low quota threshold (Warn below) defaults to 20% and can be set from 1% to 99%; it also controls warning colors even when notifications are off. Red is used only for this warning. macOS asks for permission when you enable an alert; if notifications are blocked, use Notification Settings in the app. Alerts require a successful response and a future reset date. Reset alerts arrive only after a refresh confirms a new reset period, so they may be delayed. Delivery markers and reset dates are stored locally and pruned during successful refreshes after 30 days (for reset dates, 30 days after the reset); notification records do not contain quota percentages or account identifiers. Limitwick cannot reliably detect an account switch, so alerts can be missed or associated with the previous account after switching.


## App updates

Limitwick checks for compatible releases quietly at launch and once a day. When an update is available, the context menu offers to update and shows its version. A red dot appears on the menu bar icon for an update to a new major version. Select the menu item to review and install it; update checks do not show automatic alerts. If a check fails, the last known update remains visible until a successful check finds no update or the app version changes.

## Widget


On macOS 14 or later, open the desktop widget gallery and find **Limitwick**. Choose from 24 horizontal medium widgets. Each of the six themes comes in Light and Dark for Codex and Claude. The appearance and provider are fixed for each variant. Remove the old universal widget and add your chosen variants from the gallery.

Widgets read a local quota snapshot for their provider from `~/Library/Application Support/Limitwick/Widget/` (read-only access; macOS 27 no longer lets an ad-hoc signed widget read the shared app group). Limitwick checks which widgets are installed at launch, after wake, when you refresh manually, and every three minutes. A provider with an installed widget can refresh even when it is hidden in the menu bar. Keep Limitwick running for fresh data. macOS controls when widgets redraw, so their values may lag behind the app.


## Data and connectivity

Limitwick runs `codex app-server` and reads `account/rateLimits/read`. It also listens for rate-limit events, but delivery from other Codex sessions is not guaranteed. Other window durations appear in the panel; conflicting values for the same duration are shown as unavailable.

The app does not ask for your password or store credentials. Codex contacts OpenAI, update checks contact GitHub, and the app has no separate server. Changes to the Codex CLI protocol can affect compatibility.

## Codex activity indicator

Limitwick can show activity to the left of its quota bars. Turn it on or off with “Show Codex activity in menu bar” in Settings; it is on by default, but the box stays clear until the hooks are installed, and checking it installs them. Install Codex hooks and Remove Codex hooks run the setup script below; the text under the checkbox shows whether hooks are installed and whether events have arrived. Turning it off stops the listener and hides the indicator, but leaves installed Codex hooks in place. This optional integration uses Codex lifecycle hooks. It shows a loading animation while a detected turn is working, a terminal animation while a supported tool is running, and a checkmark briefly when all detected turns have stopped. These events do not establish when an answer is being streamed or whether every kind of user input is pending, so the edit and alert animations are not used yet.

To install the hooks from Terminal instead, run the following command after installing the app in `/Applications` (adjust the app name if needed):

```sh
/usr/bin/python3 '/Applications/Limitwick.app/Contents/Resources/useAnimations/activity-setup.py' install
```

For a development build, use the same command with the path to `build/Limitwick-Development.app` instead. The setup preserves other hook handlers in `$CODEX_HOME/hooks.json` (or `~/.codex/hooks.json`); it refuses an unexpected configuration format. Review and trust the new hooks in Codex Settings → Hooks or, in the CLI, `/hooks`, and restart or reopen sessions if necessary. Hooks that have not been trusted do not run. To remove these handlers, run the same command with `remove` instead of `install`. If the app is moved, rerun setup from its new location and review the changed hook.

Hooks send only event type, session and turn identifiers, tool-call identifier, time, Codex home path and, for the Sessions window, the last component of the working folder, the launching app's bundle ID and, on `PreToolUse`, the kind of tool (`category`) to running local Limitwick instances. The kind comes from the `tool_name` that Codex CLI 0.156 sends: `Bash` (shell commands) → `shell`, `apply_patch` → `edit`, `view_image` → `read`, `web_search` → `web`, `spawn_agent` → `agent`, `update_plan` → `plan`, any `mcp__…` → `mcp`, anything else → `other`. They do not send prompts, responses, command text, tool names, tool input, or tool results. Codex 0.156 keeps hook trust as a hash of the hook's declaration in `hooks.json` (event, matcher, command, timeout), not of the script, so the copy that the app refreshes at launch runs without trusting it again as long as the command stays the same. The indicator covers only sessions whose hooks actually run while Limitwick is open. It hides a turn if the local writer lock is no longer held, including after a process crash. It does not cover remote, ephemeral, unsupported, or untrusted sessions reliably. The CLI integration was tested with Codex CLI 0.156.0; Desktop hook delivery requires separate verification. Other hooks can continue a turn after a `Stop` hook, so the checkmark reflects the observed stop event and may be followed by renewed activity.


## Claude Code activity indicator

Select Claude in Settings (Show limits, or Settings for when both services are shown) and turn on "Show Claude activity in menu bar"; if the hooks are missing, Limitwick installs them. Install Claude hooks and Remove Claude hooks add or remove only Limitwick's handlers. The setup preserves other entries in `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR/settings.json`) and refuses unexpected configuration formats. Hooks call a copy of the helper script in `~/Library/Application Support/Limitwick/useAnimations/`, which the app refreshes at launch, so they keep working after the app is moved or updated; older installations that point into an app bundle are moved to this copy. The copy is kept after removal because open sessions continue to call it until they restart. Claude Code reads hooks when a session starts: activity appears in sessions started after installation, and an open session can be included by typing `/exit` and running `claude --continue`. The status line under the checkbox reports whether hooks are installed and whether events have arrived since the app launched.

Hooks forward only the event type, session ID, tool-call ID and time to local Limitwick instances, and for the Sessions window the last component of the project folder (`CLAUDE_PROJECT_DIR`, else `cwd`), the launching app's bundle ID, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_PID` and `CLAUDE_CODE_HOST_SESSION_ID`, each validated. On `PreToolUse` the hook adds `category`, the kind of tool from a fixed table: `edit` (Edit, MultiEdit, Write, NotebookEdit), `shell` (Bash, BashOutput, KillShell), `read` (Read), `search` (Glob, Grep), `web` (WebFetch, WebSearch), `agent` (Task, Agent), `plan` (TodoWrite), `mcp` (any `mcp__…` tool), `other` (everything else); the tool name and the MCP server name stay in the hook. Permission prompts (`Notification` with `permission_prompt`) are forwarded as their own event; the menu bar indicator ignores them. Prompts, commands, responses, tool names and tool input are not forwarded. The indicator is based on observed Claude Code events, does not cover sessions without active hooks, and clears stale sessions after 30 minutes. Disabling the activity checkbox leaves the installed hooks in place.

## Sessions window

The Sessions window (`Sources/Sessions.swift`, `Sources/SessionGrid.swift`) shows up to 16 sessions of the last 24 hours; Settings limits it to 4, 8 or 16 tiles. A tile is created only by a prompt or tool event, never by a lone stop, end or notification. A turn becomes idle on `Stop`, `StopFailure`, `Idle`, `SessionEnd`, a Codex interrupt or released writer lock, when the Claude Code process ID is no longer alive, or after 30 minutes without events. A permission prompt keeps the tile waiting while its process is alive. The first folder name of a session is kept, because the working folder changes when the agent runs `cd`. A tile of a Claude app session shows the app's title instead of the folder (two lines at most; the folder stays in the tooltip): the title is read from the app's session file on each `UserPromptSubmit` and `Stop` by the `local_…` ID, retried twice 10 seconds apart after `Stop` while the file has no title yet, and on every history scan, which also picks up renamed sessions. Tiles are saved in `sessions.json` (`sessions-development.json` for the development build); turns saved before the last boot load as idle, because their process IDs may belong to other programs. A tile also saves `outcome`, how its last turn ended when it did not simply stop: `failed` (`StopFailure`), `interrupted` (Codex interrupt) or `lost` (silence, a dead process, a released Codex writer lock, a turn saved before the last boot); files without it read as a plain stop, and the next turn clears it. Open tool calls are matched by `tool_use_id` from `PreToolUse` to `PostToolUse` or `PostToolUseFailure` and kept in memory only (at most 32 per tile); a tile shows the last call started, and a new prompt, the end of a turn, silence or a dead process forget calls that never returned.

What a tile shows at a given time is `SessionLook` in `Sources/Sessions.swift`, a function of the session, its live moment, its running tool call and the time, covered by `Tests/SessionTests.swift`; `SessionGrid.swift` only draws it. Frames move in whole 4 pt pixels and change in fixed steps: a working Claude figure bobs and steps every 0.32 s, the Codex cursor blinks on and off for 0.64 s each; while a tool runs, the Claude figure types (a hand up a pixel, alternating every 0.16 s, no bobbing) and the Codex cursor runs right through three positions every 0.16 s, and the tool's icon (5 × 5 pixels of 2 pt) stands beside the head; a failed turn shows crossed-out eyes (Codex `>x`) and a silent or lost one `?` instead of z; a waiting tile's stripes move a point every 0.16 s, its light blinks once a second and the Claude figure waves three times every 3.92 s. Each session starts its cycle from a phase derived from its ID, so working mascots do not move in step. Idle tiles stand still. One clock drives every tile: 0.08 s steps while a moment plays, then 0.16 s with a waiting tile or one running a tool, 0.32 s with a working one, 20 s otherwise; with Reduce Motion, or while `NSWindow.occlusionState` says the window is covered, it stays at 20 s and every tile keeps one static pose (tool icons stay).

Moments play once, only when a hook event changes the tile and arrives within 10 seconds of its own time: a new session's pixels appear in 0.4 s; a turn ended by `Stop` shows a jump (Codex: three quick cursor blinks) and a check for 2.4 s, then the mascot greys out through a 2 × 2 dither in three steps; a Codex interrupt does the same without the jump, the blinks and the check; `PostToolUseFailure` shakes the mascot ±1 pixel for four 0.08 s frames and shows a red `!` for a second; `StopFailure` shakes it, then crosses out the eyes while it greys out. Moments are kept in memory; tiles from a history scan or `sessions.json` never play them. `Stop` and `StopFailure` set `unseen` on the tile (saved in `sessions.json`; a file without it reads as seen), shown as a green corner light (red after `StopFailure`) and a white name. A new `UserPromptSubmit` in that session, a click on the tile or **Mark All as Seen** clears it. A Codex interrupt, `SessionEnd`, silence and a dead process do not set it. A failed turn's caption is `just failed`, then `failed 3m ago`, at most 14 characters.

When the window opens and every five minutes, earlier sessions are read from disk: the Claude app's `~/Library/Application Support/Claude/claude-code-sessions/*/*/local_*.json` (app session ID, CLI session ID, folder, title, last activity, archived flag), the first 64 KB of `~/.claude/projects/*/*.jsonl` for sessions that are not from the Claude app (folder and entry point), and the first line of Codex `sessions/**/*.jsonl` (`session_meta`; threads whose `session_id` differs from `id` belong to subagents and are skipped). Files changed more than 24 hours ago are not opened. These are internal formats of other apps and may change.

A click on a Claude app session opens `claude://code/continue?session=<local_…>`. The Claude app accepts only its own session ID or `last` there and logs `invalid ?session` for a CLI session ID. This link is not documented. A session in a terminal brings the running app with the bundle ID from `__CFBundleIdentifier` to the front; Limitwick cannot pick the tab. Codex sessions from disk have no app to open yet.

The window is borderless; it is dragged by the background between tiles. **On the desktop** puts it one level above desktop icons, so it stays under other windows and in place during Mission Control.
